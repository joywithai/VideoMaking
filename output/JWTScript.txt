JWT-এর পূর্ণ নাম JSON Web Token, আর এটি একটি compact format, যার মাধ্যমে এক পক্ষ অন্য পক্ষের কাছে কিছু claims পাঠাতে পারে, যেমন user-এর identifier, token কে তৈরি করেছে, token কোন application-এর জন্য, কিংবা token কখন expire করবে, আর আমরা এখানে signed JWT নিয়ে কথা বলছি, যার তিনটি অংশ থাকে — Header, Payload এবং Signature, এই তিনটি অংশ একটি করে dot দিয়ে আলাদা করা হয়, তাই structure-টা দাঁড়ায় Header dot Payload dot Signature, এবার প্রথমে Header দেখি, এটি একটি ছোট JSON object, এখানে সাধারণত alg এবং typ থাকে, alg বলে দেয় token secure করার জন্য কোন algorithm ব্যবহার করা হয়েছে, যেমন আমাদের উদাহরণে HS256, যার মানে HMAC-এর সঙ্গে SHA-256 ব্যবহার করা হচ্ছে, আর typ-এর value JWT হলে বোঝায় token-এর type JWT, তবে Header-এর ভেতরে কোনো secret key থাকে না, শুধু algorithm সম্পর্কে তথ্য থাকে, এই Header JSON-কে UTF-8 bytes-এ রূপান্তর করে Base64URL encode করা হয়, আর এই encoded string-টাই token-এর প্রথম অংশ, এখানে মনে রাখা জরুরি যে encoding আর encryption এক জিনিস নয়, encoding তথ্যকে অন্য representation-এ প্রকাশ করে, কিন্তু encryption তথ্য গোপন রাখার জন্য ব্যবহৃত হয়, তাই Base64URL encoding-এর ক্ষেত্রে তথ্য পড়তে কোনো secret key লাগে না, Base64URL হলো Base64-এর URL-safe variant, যেখানে plus এবং slash-এর বদলে hyphen ও underscore ব্যবহার করা হয়, আর শেষের padding রাখা হয় না, এবার আসি Payload-এ, এটিও একটি JSON object, কিন্তু এখানে থাকে claims, যেমন sub-এ user-এর identifier, role-এ application-এর role, iss-এ issuer, এবং aud-এ intended audience রাখা যায়, sub হচ্ছে subject অর্থাৎ token কার সম্পর্কে, iss হচ্ছে issuer অর্থাৎ কে token issue করেছে, aud হচ্ছে audience অর্থাৎ token কোন recipient-এর জন্য, exp দিয়ে expiration time বোঝানো হয়, iat দিয়ে বোঝানো যায় token কখন issue হয়েছে, আর nbf দিয়ে বোঝানো যায় কোন সময়ের আগে token গ্রহণ করা যাবে না, এই time-related claims সাধারণত Unix epoch থেকে গণনা করা seconds হিসেবে প্রকাশ করা হয়, তবে সব claim প্রতিটি token-এ বাধ্যতামূলক নয়, application-এর প্রয়োজন অনুযায়ী এগুলো নির্বাচন করা হয়, আর Header-এর মতোই Payload-এর JSON-ও Base64URL encode করে token-এর দ্বিতীয় অংশ তৈরি করা হয়, কিন্তু মনে রাখা দরকার, encode করা মানে গোপন করা নয়, তাই password বা secret key-এর মতো sensitive তথ্য Payload-এ রাখা উচিত নয়, এবার encoded Header আর encoded Payload-কে একটি dot দিয়ে জোড়া লাগিয়ে যে string তৈরি হয়, সেটাই signing input, HS256-এর ক্ষেত্রে এই signing input এবং একটি secret key ব্যবহার করে HMAC-SHA256 হিসাব করা হয়, আর সেই output-কে Base64URL encode করলে তৈরি হয় Signature, অর্থাৎ Signature শুধু Payload-এর ওপর নয়, বরং পুরো signing input-এর ওপর তৈরি হয়, আর এই secret key কখনো token-এর সঙ্গে পাঠানো হয় না, HS256-এ token তৈরি এবং verify করার জন্য একই shared secret ব্যবহার করা হয়, তবে asymmetric algorithm-এর ক্ষেত্রে private key দিয়ে sign এবং public key দিয়ে verify করা হয়, এরপর encoded Header, encoded Payload এবং encoded Signature-কে dot দিয়ে যুক্ত করলেই তৈরি হয়ে যায় সম্পূর্ণ signed JWT, কিন্তু token তৈরি হওয়া আর বিশ্বাসযোগ্য হওয়া এক কথা নয়, কারণ server যদি শুধু Payload decode করে তথ্য বিশ্বাস করে নেয়, তাহলে verification-এর মূল কাজটাই বাদ পড়ে যায়, তাই server প্রথমে নিজের configuration অনুযায়ী অনুমোদিত algorithm ব্যবহার হচ্ছে কি না তা যাচাই করে, এরপর সঠিক key দিয়ে Signature verify করে, একই signing input থেকে expected HMAC হিসাব করে এবং received Signature-এর সঙ্গে মিলিয়ে দেখে, তবে Signature valid হলেই সব শর্ত পূরণ হয়ে যায় না, কারণ token expire করেছে কি না, issuer প্রত্যাশিত কি না, audience সঠিক কি না, এসবও যাচাই করতে হয়, আর এই কারণেই নিজের হাতে verification না বানিয়ে উপযুক্ত, maintained library ব্যবহার করা ভালো, যাকে সঠিক algorithm, key এবং claim-validation policy দিয়ে configure করতে হয়, সবশেষে মনে রাখা দরকার, Header বলে দেয় token কীভাবে secured, Payload রাখে claims, Signature দিয়ে integrity যাচাই করা যায়, আর claims validation বলে দেয় token এই মুহূর্তে গ্রহণযোগ্য কি না, অর্থাৎ decode করা মানে verify করা নয়, আর encoding মানে encryption নয় — signed JWT-এর তথ্য পড়া গেলেও, সেটা বিশ্বাস করার আগে Signature এবং প্রয়োজনীয় claims অবশ্যই যাচাই করতে হয়।
